Plate 01 · Overview

Declare a resource once. The panel checks it at mount and serves it fail-closed.

Tablo is an admin toolkit for Rust. An app declares one Resource per Toasty model; a Panel turns those declarations into list, create, edit, detail and delete pages, rendered on the server by Topcoat. There is no SPA and no client build step.

Three ideas that explain most of the code

Declare a value

A resource is a type; its settings are one value

Resource::declare() returns a ResourceDef and takes no request. Each panel builds its own copy when it mounts, so one resource type can be read-only in one panel and writable in another.

Fail early

Compile time, then mount time, then the request

Typed lenses and derives turn a renamed field into a compile error. What types cannot say, the mount refuses at startup, listing every mistake. What remains is refused per request, never served under a laxer default.

One path

One loader seam, one write tail

Every read starts from scoped_query and every record write ends in the same commit tail, commit_write. Inline cell edits, CSV import and creatable choices reuse the create and edit routes, so a check added once applies everywhere.

The smallest panel

#[derive(Debug, Clone, toasty::Model, tablo::PanelModel, tablo::ModelForm)]
pub struct Book {
    #[key]
    #[auto]
    pub id: uuid::Uuid,
    pub title: String,
}

pub struct BookResource;

impl Resource for BookResource {
    type Model = Book;
    type Form = BookForm;              // written by ModelForm

    fn declare() -> ResourceDef<Self> {
        ResourceDef::new().policy(Allow) // the default policy denies everything
    }
}

let mut builder = Router::builder().discover().with(db);
builder.panel(Panel::new("admin").resource::<BookResource>())?;
let router = builder.build();

PanelModel is the read side: it derives the default table and detail page from the model's fields.

ModelForm is the write side: it writes a BookForm struct that create and edit submissions parse into.

declare names what differs from the defaults. A policy is the one thing every useful resource must state, because the default is Deny.

builder.panel(..) is the mount. It checks the declarations against the database schema, registers routes and layers, and returns a PanelHandle for jobs and tests. Sign-in is on unless the panel says Auth::disabled().

How a lower layer asks for request state

A declaration sometimes needs something only the serving layer knows: which resources the request's panel mounts, or which tenant the session selected. It cannot import panel.

Instead the lower module owns a small type holding a function pointer, and the serving layer installs it in the router's context when the first panel mounts. MountScope answers the mounted resources, TenantSource the session's tenant, ZoneSource the time zone, CatalogSource the locale's catalog.

auth sits below panel the same way. It sees its panel only as a Realm and renders through the Host trait that panel implements, so it names no panel type. Before this, auth named the panel in 19 files.

Plate 03 · Deep dive

From declaration to a mounted panel

Panel is a builder that checks nothing. All validation happens in one call, builder.panel(panel), which either returns a PanelHandle or a MountError listing every declaration mistake at once.

What Panel::mount does, in order

Where a mistake is caught

The design keeps moving errors to the left of this table. When you add a feature, ask which column each misuse lands in.

compile

  • A renamed or retyped field: lens! and the derives name it.
  • A toggle column over a String, or a control from another form in a Schema<Form>.
  • A tenancy lens to a column that is not TenantId.
  • An exhaustive policy that does not answer a new Ability variant such as RunHeader.
  • An action NAME that is not a URL segment (a checked constant).
  • An auth seam written for a different user type than the authenticator's.

mount

  • A resource over tenant-owned rows that declares no tenancy.
  • A file field on a panel with no Uploader, or a file limit above the body cap.
  • An editable cell whose form control would not save what the cell posts.
  • A computed or custom column that could show a field another resource restricts.
  • A create that leaves a non-nullable column unset.
  • A duplicate or reserved slug, a prefix overlapping another panel, a model the Db does not register.

request

  • No session: redirect to login for a page, 401 for anything else.
  • No tenant on a tenant-scoped resource: 403, never unscoped rows.
  • A row outside the scoped query: 404, as if it did not exist.
  • A posted key the user may not change: 400, since no browser posts it.
  • A missing or wrong CSRF token: 403.
  • Invalid input: the form again with errors, nothing written.

What the mount leaves behind

Mounted<R> is the def with every default filled in: slug and labels from the type name, the table and detail from PanelModel when none is declared, form fields the layout did not place appended in declaration order, the trash filter and its two actions when the resource soft-deletes.

PanelState holds one panel's registries: its Mounts keyed by resource type, sidebar entries, trails, areas, searchables, commit hooks and loaders. The router's context holds a Panels list of them; each request enters exactly one.

Type erasure happens here. Handlers are generic functions such as resource_list::<R>, registered as plain route functions. Cross-resource registries (search, trails, relation tables) store function pointers that return BoxFuture, so the non-generic machinery compiles once in tablo-core.

Routes exist only for what is declared. A list-only resource gets no form route; action, link, import and column-picker routes are registered only when the def uses them. List-level routes sit under a reserved - segment, as in /admin/posts/-/export, so no record key can collide with them.

// Two panels, one resource type, two mounts.
Panel::new("admin")
    .resource::<PostResource>();

Panel::new("portal")
    .resource_with::<PostResource>(|def| {
        def.policy(ReadOnly)
           // each author lists and opens their own posts only
           .query_fn(|cx| Post::fields().author().eq(me(cx)))
    });

// A job reaches the mounted panel through its handle.
let handle = builder.panel(panel)?;
let cx = handle.context();

    Policies cannot await. A policy, a query_fn and a condition are asked once per row and per button from code that renders, so they are synchronous. Whatever they need from the database, a type implementing Load fetches once, right after the gate admits the request.

    Panel has no type parameter. The user travels erased and is read back by type. A value the gate never set is absent, so a policy reading it fails closed.

    Handlers do not trust the layer. Every resource handler starts with gate::<R>(cx): auth::guard, then require_mounted, then enforce_tenant.

    Sessions and the runtime path

    Sessions

    Server-side rows, one cookie per panel

    A session is a row keyed by the token's hash, rotated on login, revocable per user, valid seven days. Each panel has its own __Host-tablo_session_… cookie, so a browser stays signed in to several panels and never overwrites the host app's Topcoat session.

    Runtime requests

    Served outside every prefix

    Topcoat's runtime endpoints live at /_topcoat/runtime. RuntimeGate covers them. A fetch names its page in the Referer; a socket's runs carry a header stamped from the handshake URL. That name only picks which cookie counts, so forging it grants nothing.

    Opt-in seams

    One trait per feature

    Authenticator is required. Sign-up, profile, password reset, email verification, tenant registration, OIDC and external auth are each a trait the app implements for the same user type. PasswordAccount covers a plain email-and-password table with one impl.

    Plate 05 · Deep dive

    The read path: a list page and its re-runs

    Tablo ships no table script. A table keeps its list query in a Topcoat signal; a sort, filter, search or page change writes the signal, and the runtime re-runs the same page through the same route and guards.

    One request to /admin/posts

    The URL is the state

    TableState parses the query string without knowing the table: search, sort, cursor or page, per-page, tab, grouping and filters. Links carry a real href and the toolbar is a GET form, so reading works without JavaScript.

    A filter's value uses form encoding's own repetition. A multiple choice repeats the parameter; a range submits its ends as named parts. Each filter then decides what it accepts, and a value it rejects is shown as an ignored filter, never half-applied.

    Pagination has three modes: Pages counts the result set, Simple does not, and Cursor neither counts nor skips rows, so it does not drift on a fast-changing table.

    /admin/posts
  ?q=release                  search
  &sort=-created_at           sort, descending
  &tab=drafts                 list tab
  &f.status=draft             filter, one value
  &f.status=review            ...repeated: a list
  &f.created.from=2026-01-01  filter part
  &f.created.to=2026-03-31    filter part
  &f.trashed=only             the trash control
  &page=3

    Relations are includes, declared where they are read

    There is no Relation trait. A column declares the relations its cell reads as typed Toasty includes, and the list, the export and the detail page load exactly what their columns declare. A relation column also names the resource R whose rules govern the related records.

    After the rows load, Column::restrict runs one more query through R's scoped query and records which related records the request may see. A cell renders only those. The rows themselves keep what the include loaded, so a policy or a title reading the same relation still sees it whole.

    The include stays unfiltered on purpose: Toasty 0.11 panics on a filtered include over a via relation, and a required belongs_to has no shape for a filtered-out record.

    Where JavaScript does exist

    Scripts enhance single controls the runtime has no word for. Each acts on the form's own inputs, so the submission is the same body with or without it.

    Plate 06 · Deep dive

    Who sees which rows, records and fields

    Three separate mechanisms answer three separate questions. Mixing them up is the most common design error, and several ADRs exist to keep them apart.

    QuestionMechanismRunsGranularity
    Which rows exist for this request?scoped_query: query narrowings, tenancy, trashIn the database, as a predicateRow. A row left out answers 404.
    What may the user do?Policy::allows(cx, Ability)In Rust, synchronously, per row and per buttonAbility, optionally on one loaded record. Refusal is 403.
    Which fields may the user see or change?ResourceDef::field_access and the request's FieldMaskOnce per request, over the request aloneField of a model, across every resource the panel mounts over it.

    Row visibility never goes through the policy's View: a policy runs in Rust, so rows it dropped would still count toward the page, the option cap and the totals.

    Compose a scoped query

    Every loader starts from Mounted::narrowed. Toggle what the resource declares and which records the caller asks for.

    Who asks for this scope

    Each narrowing is ANDed, so a panel's resource_with can only narrow what declare narrows. A narrowing is a predicate, never a closure over the query: it cannot order, limit or drop a filter, and the framework can read which fields it names. The unique pre-check relies on that: it keeps a narrowing that reads a field of the index it probes and drops one that reads none.

    What each operation asks of the policy

    The same abilities decide which buttons render, so a hidden button is also a refused request. Writes ask about the row loaded inside the transaction, not the submitted key. Run has one answer that the button, the route and can() all read: the mounted policy allows it and the action's own can_run admits the record.

    Field access masks the panel, not a page

    A rule is a predicate over the request, not the record: a column, a filter or an export header exists for the whole page or not at all, so a per-record rule would leak through the header, the sort and the CSV.

    The rule restricts the field of its model within the panel. Every resource the panel mounts over that model masks it the same way, in tables, filters, grouping, detail entries, relation columns, choices and exports.

    Anything the panel cannot see into must declare what it reads. A ComputedColumn, a QueryFilter or a custom column says so with .reading(..); one that does not is refused at mount wherever a rule could apply.

    On the write side the record form is a typed struct, so a masked field still takes a value: the stored one on an edit, the default or blank answer on a create. Posting the key anyway answers 400.

    The write path: one transaction, two hooks

    Every mutation runs in a framework-owned transaction. Parsing and validation happen before it opens, so no option loader waits on the connection it holds. The record is loaded and authorized again inside it.

    The hooks and what they receive

    pub enum Change<M> {
    Create(M),
    Update { before: M, after: M },
    Delete(Vec<M>),
    Restore(Vec<M>),
    ForceDelete(Vec<M>),
    Action { name: &'static str, records: Vec<M> },
    HeaderAction { name: &'static str },
    Attach { owner: M, relation: String, key: String },
    Detach { owner: M, relation: String, keys: Vec<String> },
}

// Inside the transaction: commits with the write or not at all.
async fn before_commit(cx: &Cx, change: &Change<Post>,
                       ex: &mut dyn Executor) -> Result<()>;

// After the commit: effects outside the database.
async fn after_commit(cx: &Cx, change: Change<Post>) -> Result<()>;

    before_commit runs through the open transaction. An error rolls the whole write back. This is where an audit row or a counter belongs. Opening a second connection here is refused, because on a pool of one it would wait forever.

    Panel-wide CommitHooks run right after it, with the change erased to a PanelChange. tablo-audit is one.

    after_commit is for mail, webhooks and cache invalidation. It never runs when nothing committed, and nothing guarantees it runs: an error is logged and ignored, and a crash between the commit and the hook skips it.

    WriteError has three shapes. Refused carries field errors and re-renders the form. Declined carries a message with no field. Failed is a driver error, shown as an opaque toast after a second unique probe.

    No second write path

    Features that look like new endpoints are routed through the existing ones, so the next check added to a create or an edit cannot be missing from them.

    Plate 08 · Deep dive

    Typed bindings: the model is named once

    Nothing binds to a field by a string. A lens pairs a field's query path with its reader; two derives split the model into a read side and a write side. Strings appear only on the wire.

    Read side and write side

    read · PanelModel

    What a person reads

    • columns(): one FieldColumn per readable field, named like the field.
    • table() and detail(): the defaults a resource uses when it declares neither.
    • TENANT_COLUMNS: the TenantId fields, which the tenancy check reads.
    • version() for stale-save detection; bare(), a copy without relations.
    Toasty modelstruct Post { .. }
    write · RecordForm

    What a submission writes

    • A struct with one field per written column, typed like the model.
    • controls(): the only controls a Schema<Form> accepts.
    • hydrate a record into form values; parse them back, the single presence and type check.
    • into_create and into_update: Toasty's own builders.

    The two are deliberately separate. A form leaves out what Toasty writes, such as a defaulted timestamp, and a list-only resource has no form at all (NoForm<M>); the model still has both views. ModelForm writes the form struct from the model when the two coincide.

    The lens

    pub struct Lens<M, T, P = T> {
    path: Path<M, P>,       // what queries filter and sort on
    read: fn(&M) -> &T,     // what reads the value off a row
}

// One field name writes both halves.
macro_rules! lens {
    ($($model:ident)::+ . $($field:ident).+) => {
        $crate::Lens::new(
            <$($model)::+>::fields()$(.$field())+,
            |record: &$($model)::+| &record$(.$field)+,
        )
    };
}

TextColumn::new(lens!(User.name)).searchable();
Tenancy::column(lens!(Post.tenant_id));
ResourceDef::new().soft_delete(lens!(Post.deleted_at));

    A column needs both halves because it renders the value it sorts on. Since lens! writes both from one name, they cannot name different fields.

    A lens binds when the declaration is built, with no database connection. A path into an embedded value resolves to the flattened column Toasty names, read off the schema Toasty compiles for the model. Tablo does not re-derive Toasty's naming rule.

    A chain through a relation does not compile: a relation's records are not part of the row. Relations use relation!, which pairs an include with its loaded-value reader.

    Two type-level details worth knowing

    Column picking

    FieldColumn is a function per place

    The derive picks a field's column by autoref specialization over its type. That works only in an expression, so no struct field can name the picked type. The handle keeps the pick as one function per place: a timestamp is a sortable day in a table and the stored instant on a detail page. This is why a table takes anything IntoColumns.

    Closed sets

    Options live on the enum

    A closed set of values is a unit enum deriving toasty::Embed and Options. A choice field, a select filter, a column and a group header all read its options and labels from the type, and a query compares a variant, never its spelling.

    Plate 09 · Deep dive

    Extension points

    There is no plugin trait. An extension is a type implementing one small trait, registered through a builder method an app could call itself.

    The seams, by what they add

    TraitAddsRegistered with

    The building-block traits are gathered in the public extend module. Each follows the resource's shape: a declare() that returns one def value, plus the methods that validate and run.

    Proof by construction: tablo-audit

    The audit log was first wired through the core's private state. Whatever it reached privately was exactly what an app building the same kind of feature could not reach.

    So it moved to a crate of its own that sees only the public API, and the core gained each seam it needed. The crate is an extension trait on Panel that registers a commit hook, an auth hook, a required model, catalogs and an ordinary resource.

    Use it as the reference for a cross-cutting feature: if your extension needs something this table does not offer, that is a missing seam in the core, not a reason to reach into PanelState.

    Conventions an extension must follow

    API shape

    One path, no bool switches

    Types sit at the crate root. A feature off by default turns on through a method named after it (importable()); one on by default turns off through without_<feature>().

    Compile cost

    Keep generics thin

    Code generic over a model or resource compiles again in every app crate, once per type. A view built from strings goes in a free function, and a future only a generic caller awaits is returned as BoxFuture.

    Words

    Every label is a Text

    A word a page shows is a Fluent message with a tablo- id; a label a builder takes is a Text, rendered where the request's locale is known and never at mount. Operator-facing errors stay English.

    Plate 11 · Critical insights

    Trade-offs and fragile ground

    Where the design pays for its choices, where it leans on upstream behaviour, and what a new maintainer should treat carefully. Each item names the source that documents it.

    The trade the whole design makes

    Tablo buys one path per effect and early refusal with breadth of declaration-time checking. The mount has to understand every way a declaration can combine: an editable cell against a form control, a computed column against another resource's field rule, a related form against a soft delete.

    That is why panel is the largest module and why DeclarationErrorKind has a fault enum per feature. A new feature is not finished when it renders. It is finished when every other feature's guard covers it: list, detail, export, global search, relation table, import.

    The contributing guide states the review rule this produces: fix the class, not the instance.

    Before you change shared code

    A guard on one page must cover every page with the same effect. A change to a shared helper is checked at every caller.

    Security checks fail closed: a missing tenant, policy, session or CSRF token refuses the request.

    There are no compatibility shims: delete the old path in the PR that makes it dead.

    A workaround that needs a paragraph of comment means the code is wrong.
